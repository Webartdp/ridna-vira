# Користувачі, ролі та особистий кабінет

Адміністратор керує обліковими записами в **Доступ → Користувачі та ролі**, адреса `/admin/users`. Можна створити користувача, змінити ім’я/пошту, призначити одну з чотирьох ролей, заблокувати доступ та встановити новий пароль. Порожнє поле нового пароля під час редагування зберігає наявний пароль; хеші не показуються у формі. Замість видалення користувача використовується блокування.

| Роль | Доступ |
| --- | --- |
| Адміністратор | Усі розділи адмінки, користувачі, налаштування сайту й оплати |
| Редактор | Сторінки, новини, статті, творчість, віра, медіафайли, календар, громади та мапа |
| Менеджер крамниці | Товари, категорії, замовлення, виконання замовлень і скасування неоплаченого резерву |
| Користувач | Особистий кабінет на публічному сайті; без доступу до адмінки |

Ролі фіксовані. Права перевіряються політиками моделей і сторінок, включно з Livewire-діями. Редактор і менеджер не можуть керувати користувачами або платіжними секретами. Свою роль адміністратора не можна понизити або заблокувати; також захищено останнього активного адміністратора. Зміни доступу зберігаються в `user_access_audits` без паролів. Доступ MCP залишається лише для активних адміністраторів із чинним окремим токеном.

## Публічний кабінет

- `/reiestratsiia` — реєстрація. Роль завжди «Користувач», незалежно від надісланих полів.
- `/uviyty` — вхід, запам’ятовування сесії, посилання на відновлення пароля.
- `/kabinet` — власні замовлення й статус підтвердження пошти.
- `/kabinet/profil` — ім’я, пошта, телефон, адреса доставки та зміна пароля. Збереження потребує поточного пароля.
- `/parol/vidnovyty` — запит листа для скидання пароля. Токен одноразовий і має термін дії.
- Кнопка кабінету є в шапці сайту. У кошику підставляються контактні дані профілю. Гостьове оформлення залишається доступним.

Нові замовлення авторизованого покупця прив’язуються до його `user_id` на сервері та автоматично з’являються в історії. Чужі замовлення не відкриваються за підстановкою ID або номера. Старі гостьові замовлення не приєднуються лише за збігом email: потрібно відкрити особисте посилання замовлення й натиснути «Додати до кабінету», увійшовши з тією самою підтвердженою поштою. Замовлення іншого користувача переприв’язати не можна.

Після зміни пошти її треба підтвердити повторно. Зміна пароля завершує старі сесії під час наступного звернення до захищеної сторінки. Заблокований обліковий запис не може увійти або продовжити роботу в кабінеті, адмінці чи MCP. Приватні сторінки не кешуються й закриті від індексації та sitemap.

## Листи

Листи підтвердження адреси та відновлення пароля — українською. Потрібна робоча пошта Laravel у серверному `.env`: `MAIL_MAILER=smtp`, налаштування SMTP-провайдера, `MAIL_FROM_ADDRESS` та `MAIL_FROM_NAME`. Пароль SMTP задається лише на сервері. Для коректних підписаних посилань має бути `APP_URL=https://ridnavira.com.ua`; бажано також `APP_NAME="Рідна Віра"`.

Відправлення перевірене через тестові notifications; реальну доставку SMTP на робочому сервері треба перевірити після деплою. Кабінет і нові власні замовлення доступні також до підтвердження адреси. Підтвердження обов’язкове для приєднання старих гостьових замовлень.

## Статті в адмінці

У `/admin/articles` є компактний список з обкладинкою, назвою й коротким описом, статусом і датою зміни. Довгу адресу приховано за замовчуванням; її можна ввімкнути у виборі колонок. Основна дія — «Редагувати», решта дій зібрані в окремому меню. Пошук за назвою/адресою збережено. Статуси розрізняють опубліковані матеріали, чернетки, заплановані публікації та кошик.

## Деплой

Нових Composer/npm-залежностей та змін CSS/JS-збірки немає. Потрібна міграція БД. Перед деплоєм збережіть резервну копію бази штатним способом сервера.

```bash
sudo -u ridnavira-com-ua -H /bin/bash -c '
set -e
cd /home/ridnavira-com-ua/web/ridnavira.com.ua/public_html/app
php artisan down
git pull --ff-only origin feature/site-build
php artisan migrate --force
php artisan optimize:clear
php artisan filament:optimize-clear
php artisan view:cache
php artisan route:cache
php artisan up
'
```

Міграція переносить чинних адміністраторів із `is_admin=true` у роль `admin`, зберігає їх активними та залишає старі замовлення гостьовими (`user_id=null`). Паролі чинних користувачів не змінюються. Команди `site:admin` та `site:admin-reset` створюють/відновлюють активного адміністратора, як і раніше.

Після деплою перевірте `/admin/users`, `/admin/articles`, `/reiestratsiia` та `/kabinet`. Зробіть тест реєстрації й доставки листів на власну адресу, перевірте ролі редактора/менеджера окремими сесіями та доступність особистої історії замовлень.
